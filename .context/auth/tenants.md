# Auth: tenants and guests

Part of [Authentication and authorization](README.md). Tenant isolation, and guests from linked servers.

## Tenants

Every organization is a **tenant**, under the one **root** organization (`auth.ROOT_TENANT`, `"root"`; `orgs.parent` is `"root"` for every other, `None` for it). Nothing crosses tenants, except site admins: they see and control everything in every tenant, to look after the server. Check the tenant first, before roles, sharing or grants: `auth.same_tenant(identity, tenant)`, which is false for a missing tenant (fail closed), and true for a site admin whatever the tenant. On top of it, `access.can_view`/`can_control` and `fleet.allowed` answer yes for a site admin (private sessions, every machine feature), and `fleet.runs_containers` lets them manage containers anywhere. `access.is_owner` stays the owner's alone, so "delete all my sessions" and changing a session's sharing never reach other people's.

- **Users** (`users.tenant`, `Identity.tenant`): exactly one tenant each, set when made and never changed (`UserStore.update_user` refuses `orgs` that differ, `set_membership` refuses joining or leaving an organization). `Identity.orgs` is `(tenant,)`; teams are only that tenant's. `role` is per tenant: `Identity.admin` is an admin of their own organization; `Identity.site_admin` is an admin of the root, which takes only admins. Because a user's tenant never changes, anything stamped with it at creation stays correct.
- **Roles at the boundary**: `auth.SITE_ADMIN_ONLY` (server settings and everything under `/api/config`, restart, server stats, the access log, making and removing organizations) needs `site_admin`; `auth.ADMIN_ONLY` (which includes it, plus containers, adopting a provider, legal holds (`/api/holds`), `/api/orgs/*`, `/api/users/*`) needs `admin`, and the route then checks which organization: `auth.administers(identity, tenant)` (its admins, and site admins for the directory of any). Others answer 404, not 403.
- **Sessions**: the server-set tag `tenant` (in `access.SHARING_TAGS`, so clients can't set it), from `access.sharing_tags` (every launch and `/api/sessions`) and `Runtime.resolve_session` (implicit sessions). `access.can_view`/`can_control`/`is_owner` start with `in_tenant`. Requests, traces, chats, live events, terminals and MCP all go through those, and `/api/status` token totals add up only visible sessions (`Runtime.tokens`, per session).
- **Machines**: `Machine.tenant`, its first owner's, set in `Fleet.connect`, which refuses the same id from another user or tenant. `fleet.owns`/`allowed`/`can_manage` start with the tenant; grants (`checked_access`) only name the machine's own organization and its teams, and `granted` ignores any others. `removed_for`, `machine_for`, launch verification and tunnel attach check it too.
- **Backends** have no tenant column: `Fleet.backend_tenant` derives it from the machine (nobody's once the machine is gone), from the `org` option for a hosted `api` backend (`api_providers.owner`; none is the root), the root's for a machine type without a machine (from before machines), and `Fleet.SHARED` for the `anthropic` pass-through (site admins' Server settings; agents bring their own credentials). An `api` backend carries a key, so it isn't shared: `Fleet.api_tenants` (its own tenant, plus for a hosted one its `orgs`, `"*"` every tenant) decides, in `usable_by` and `routes/providers.py`; within its own tenant `teams` (`api_providers.for_teams`; none listed is everyone) limits it, except for that tenant's admins. Its tenant's admins manage it at `/api/orgs/{org}/providers` (`routes/api_providers.py`: `managed` checks `administers`, the tenant before anything else; a name another tenant uses is a `409` that doesn't say what it is; `orgs` only from site admins; `fallback` and `teams` only the tenant's own); site admins also at `/api/config/providers` (`SITE_ADMIN_ONLY`). Removing an organization removes its hosted providers and keys, its machines, usage limits and retention policy, and leaves its sessions tenantless (site admins only); removing a user removes their machines, provider accounts and own usage limits (`UsageLimits.remove_user`) and disowns their sessions and `launched_by` tags (`routes/auth.remove_org`/`remove_user` + `offboard`): a recreated name inherits nothing. Legal holds block removing the organization. The CLI (`agent-server user remove`) removes the account and its usage limits (database rows, no running server needed); machines, provider accounts and session ownership need the running server, so remove people in the console when they had any. `Fleet.usable_by(identity)` is the filter every backend lookup for a user takes: `Settings.backend(name, usable)`, `Settings.backend_for(..., usable)`, compat's `_backend` (so `X-AI-Proxy-Backend` can't reach another tenant's), `/api/agents`, `/api/models`, `/api/status`. Containers are reachable only through a visible machine (`routes/containers.py` `mine`). Backend names stay unique server-wide. **Shared models**: site admins can let every organization use some models of one of the site's own providers (`Settings.shared_models`, `{backend: [model]}`, `"*"` all; `PUT /api/config/shared-models`). `Fleet.shared_with_all` applies a share only while the backend's tenant is the root (never a link backend), so it can never hand one organization's machine or key to the others. `usable_by` takes shared backends too, and `Fleet.model_limit(identity, backend)` is `None` when the caller may use every model (`_usable`, the rule above), else the shared models. Every place that sends a model upstream or starts work checks it before anything goes out: `compat._check_model` (`_forward` POSTs, `_native_chat`), `_fallback`, `prepare_agent_session`, `routes/machines.launch`; lists filter by it (`/v1/models`, `/api/tags`, `/api/ps`, `/api/models`), and `/api/status` gives such callers only the type. A relayed request or a guest's session (`allowed_backends`) is its bridge's to decide. `tests/test_shared_models.py` covers it.
- **Migration** (`db/migrate.py` step 2, `_tenants`): each user to their first organization by id (admins in none to the root, members in none to `main`), teams of other organizations dropped, sessions and machines to their owner's tenant (ownerless ones to the root). Frozen in the step; don't make it call `auth.py`.

## Guests of linked servers

Peering (`links.py`, `bridges.py`) is the second, narrow exception to "nothing crosses tenants". A linked server authenticates with its link key, never through the issuer: no account, service client or token is ever made for it, so it can never call an ordinary route. Its routes (`/api/links/present`, `/api/links/connect`, `/api/links/relay/*`) are public paths in `AuthMiddleware` (`PEER_PATHS`, `PEER_PREFIX`) on purpose, and each calls `Links.verify` first: link known and not paused, sender's mesh id, a current key, `mesh-date` within 30 s, a fresh nonce (shared cluster key), the body's digest, the signature over method, raw path and query, and the assertion's link, sender, receiver and lifetime. Requests carried over the link socket arrive through the app with `scope["state"]["link_channel"]`, which must match the link they claim. The site admins' `/api/links*` routes are `SITE_ADMIN_ONLY` and also check `site_admin` in the route (they sit beside the public peer routes, registered after them).

Someone of the other server is a `bridges.Guest` (the peer's per-user id `user_uuid(name, created_at)`, name, organization, teams, link, bridge): its own type, refused by `same_tenant` and `administers` by type, so by every helper built on them (`can_view`, `can_control`, `fleet.allowed`, `usable_by`, `mcp.usable`). A guest is served only through `bridges.checked` (the bridge is this organization's with the assertion's, active, both policy digests current, the item let out) and `bridges.can_view` (a launch it started, over that bridge). A guest's launch is the machine owner's session with server-set `PEERING_TAGS` (`access.SERVER_TAGS`, so clients can't forge them); its organization's admins and the machine's owner see it. The receiving side's people reach what crosses only through `bridges.lets_in` (their organization's bridge, their teams); a `link` backend is its organization's alone. The other server's statement of who its people are is trusted within what's let out. A removed user is announced to linked servers (`bridges.offboard`), which end their guests' work.
