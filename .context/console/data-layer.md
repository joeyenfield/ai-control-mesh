# Console: data layer

Part of [Console (`ui/`)](README.md). `api.ts`, query keys, polling, live updates, and page-specific data rules.

## Data layer

`OllamaInstall.tsx` shows a machine's install options on the Ollama server page, including when it is missing (`install_available`). The user explicitly chooses CPU, Android Vulkan or Adreno/Turnip; CPU is suggested. The page polls Ollama settings for job progress, prevents installation while running or with unsaved settings, and replaces its draft with the installed profile on completion. Management uses `you.servers`, including delegated server grants. GPU setup is visibly unverified until the user tests model replies. The demo phone supplies these options; `docs/screenshots/ollama-install.png` shows the chooser.

`Costs.tsx` exposes `?tab=missing` (Missing prices), filtering the existing `org-costs` report's model rows by `unpriced > 0`, sorted by unpriced calls. It includes unnamed models, supports name search, and follows the same organization/date scope and server permissions as Summary. It does not match price patterns or infer missing prices from zero cost; recompute refreshes the report after prices change.

Session review model rows can have a null `tier` when none of their calls used tokens. `SessionReview` shows these as No token usage without indexing the tier labels; they are distinct from paid models with no price. The server's aggregated `traffic.tiers` contains only classified calls.

Machine setup codes grant one use per computer even when both programs are installed: their login is shared. The Machines page accepts 1-100 machines, sends that count as uses, and asks for one device approval in the native and sandbox instructions. Both setup-code environment variables remain in native commands because either program can sign in first.

`Downloads.tsx` keeps its two command switches in page state, not `localStorage`: the install switch (`INSTALL_CHOICES`: both programs, `--only agent`, `--only agent-machine`) and the uninstall switch (`UNINSTALL_CHOICES`: keep their data or purge it). Purging signs `agent` and `agent-machine` out of every server they're signed in to, which revokes their tokens, then deletes their settings, sign-ins, logs and caches, so it is never the default; the line under the switch says what the chosen one does, and the command below carries the option itself. Both commands come from `installLine()` and `uninstallLine(server, system, { only, purge })`, exported from `Downloads.tsx` so `JoinSteps` and `RemoveSteps` emit the same strings; no page writes the option syntax itself, and what they emit matches `uninstall.sh`'s `sh -s --` form and `uninstall.ps1`'s `[scriptblock]::Create((irm ...))` form rather than a bare `iex`, which cannot take parameters.

`ServerStats` OS measurements can be null on restricted systems such as Termux. `ServerStatsPage` preserves null chart samples, omits meters without usable measurements and labels missing memory and uptime data as unavailable; it never converts a denied probe into zero usage. A CPU count of 0 is unavailable, so the process CPU chart cannot be normalized then.

- **`api.ts`** is the only place that calls `fetch`. `request<T>()` turns non-2xx responses into `ApiError(detail, status)`. `export const api = {...}` groups the methods by area. Standalone helpers cover streaming and shaping: `pullModel` (NDJSON progress), `fetchProviderLog`, `terminalSocketUrl`, `machineProviders`, `providerRef`, `addBackend` (hosted APIs only). The stored settings have their own methods and types: `api.storedAgents`/`saveAgent`/`deleteAgent`/`resetAgent` (`StoredAgent`: id, definition, yaml, builtin, edited), `api.modelTuning`/`modelTuningYaml`/`saveModelTuning` (`ModelTuning`: defaults, profiles, aliases), `api.storage`/`saveRetention` (`StorageInfo`), `api.importSettings`; `api.requests(query)` takes a `RequestQuery` (`session_id`, `limit`, `before`, `model`, `kind`). Its types must mirror the Python response shapes.
- **Provider addressing**: `/api/machines/{id}/providers/{kind}-{port}`. A `ProviderRef` is `{machine, provider}`. `MACHINE_TYPES = ["ollama","llamacpp","strata","docker"]`. `API_TYPE = "api"` is the generic OpenAI-/Anthropic-compatible backend, hosted or on a machine (a machine reports it with a `flavor`: `lmstudio`, `vllm`, `sglang`, `openai`; `API_FLAVORS` names them); `routes.ts` `isHosted(backend)` (Anthropic, or `api` with no machine) decides the hosted route, never `type === "anthropic"` alone.
- **Query keys**: shared ones in `hooks.tsx` (`useStatus` `["status", "summary"]` and `["status", "recent"]` every 2 s (invalidate by the `["status"]` prefix), `useSessions`, `useRequests(sessionId?)` `["requests", sessionId, revision]` (one session's all, or everyone's newest `REQUEST_WINDOW` = 2000; the Requests page fetches older pages on demand with `before`, "Load 2000 older"), `useModels`, `useMachines` every 5 s, `useAgents`, `useAuth`, `useVersion` `["health"]`). Others: `["terminals", "open"]` (the rail) and `["terminals"]`, `["containers"]`, `["remote"]`, `["config"]`, `["stored-agents"]` (saving one also invalidates `["agents"]`), `["model-tuning"]` (saving it also invalidates `["models"]`), `["storage"]`, `["api-providers"]`, `["orgs"]`, `["users"]`, `["mcp"]`, `["downloads"]`. Per machine: `["provider", m, p]`, `["metrics", m]`, `["ollama-settings", id]`, `["ollama-log", id]`, `["llamacpp-settings", id]`, `["llamacpp-install", id]`, `["llamacpp-log", id]`, `["provider-log", m, p, source]`, `["container-log", name]`, `["machine-folders", id, path]`. After a mutation, invalidate the keys it affects. Logout, adopting a provider, adding a backend, saving Settings and creating or deleting a container invalidate everything (sign-in is a full-page redirect).
- **Session chat** (`components/SessionChat.tsx`, the Chat tab of `pages/Session.tsx`): `["chat", session, thread]` is an infinite query, newest page first; a change in the session's request count refetches only the newest page and folds it in. `["chat-turn", session, thread, index]` fetches one turn whole when a preview is opened. `buildItems` turns the server's turns into messages, and it decides by the server's `author`/`note`/`kind`, never by role alone: `person`/`parent`/`unknown` (and a background call's own instructions) on the right, assistant and unpaired tool output on the left, the agent's own text as centred notes (reminders and notes only with **Show what … added**). Don't re-derive who wrote something in the browser: add it to `chat.py`. The thread list is the side column at 900 px and up, a `<select>` below.
- **Session review** (`components/SessionReview.tsx`, the Review tab of `pages/Session.tsx`): `["session-review", session]` (`api.sessionReview`) is the server's measurements, findings, score, prompts, reviewers and earlier reviews; nothing is measured or judged in the browser. `Evidence` draws the timeline (an inline SVG line) and the context's parts (a bar in the `--series-*` colours) and lists the rest in `Table`s that open. Findings are `<details>` (high ones open, the rest by choice; area chips filter them), and the verdict at the top only counts what the server sent: its score (`ScoreRing`, an SVG arc), `score_breakdown` and `area_scores` (`review-meter` bars, buttons that set the area filter), `security` (its own bar below a rule that filters to the `security` area, or **not checked**/**off** when it is null; its exposures and sources, already masked by the server, are `ExposedDialog`, opened by **See what was exposed** at the top and on each security finding, and a `Table` in `Evidence`, both from `exposureRows`), and each finding's `penalty` (security points for a security finding). **Review this session** calls `startReviewRun` in `reviewRuns.ts`: a module-level store (`useSyncExternalStore`), not component state, so a review goes on when the tab unmounts (**Open as a session**, any other page) and is found again on return. It calls `api.startReview` (backend, model, prompt id, question), which returns a new session and the messages the server wrote, sends them with `askModel` (falling back to `followReply` after a dropped connection, as Ask a model does), then ends that session and invalidates the query; `pagehide` ends the sessions of runs under way, since a closed page can't read the reply. Never abort a run from a component's cleanup. `LiveReview` reads the run (phase, clock, the model's reasoning, the answer); the rest of the tab reads only `useReviewPhase`/`useReviewRunId`, so it doesn't redraw with every word. The model list is the server's `reviewers` joined with `useModels`. An earlier review's text is `["session-review-text", session, review]` (`api.readReview`). `spaced()` puts blank lines round a model's headings so `Prose` shows them as headings. The prompts are the server's setting: `components/ReviewPrompts.tsx` (`ReviewPromptsSettings`, Server settings' **Review prompts** tab, `?tab=reviews`) edits `["review-prompts"]` as YAML the server checks, and saving invalidates `["session-review"]`; its **Security scan** select saves `security_scan` (`api.saveSecurityScan`) the same way.
- **Live**: only `live.ts` `useLive(sessionId?)` opens the EventSource (and `followReply` in `api.ts`, for Ask a model). It folds the `snapshot`/`start`/`summary`/`delta`/`end` events into a ref and publishes once per animation frame. An EventSource that ends up `CLOSED` (a reconnect answered 401, 502 or 503) never retries by itself, so both call `renewSignIn(opened)` (exported from `api.ts`, wrapping the shared refresh; a renewal made since the stream opened counts) and open a new one after `LIVE_RETRY_MS` (1, 2, 5, 10, 30 s); `useLive` also reconnects at once on `online` and on `visibilitychange` to visible. Every new connection starts with a snapshot, which resyncs. The server ends a stream when its access token expires and sends `retry: 1000`, so the browser reopens it a second later; `useLive` reports disconnected only after a gap longer than `LIVE_GAP_MS` (4 s). `followReply`'s retries stop with its 60 s quiet timeout, which reopening doesn't reset.
- **Idle**: `idle.ts` `watchIdle(queryClient)` (called once in `main.tsx`) owns TanStack Query's `focusManager`: the page counts as focused only while its tab is visible and some input (pointer, key, wheel, touch, scroll) came in the last `IDLE_MS` (2 min). Unfocused, every `refetchInterval` skips its fetches (except queries with `refetchIntervalInBackground`), and while idle and visible the active polled queries refetch once every `IDLE_REFRESH_MS` (60 s). The first input refocuses, so stale queries refetch at once. Don't call `focusManager.setFocused` or `setEventListener` elsewhere. SSE and terminal sockets aren't affected.
- **Polls after errors**: `pollEvery(ms, afterError)` in `hooks.tsx` is the `refetchInterval` for polls with `retry: false` (the rail's `["terminals"]` and `["machines"]`, a machine's terminals): after an error it keeps polling every `afterError` (20 s by default), stopping only on a 403. `["remote"]` on Running agents polls every 10 s while it fails. The other shared queries use a plain number, which TanStack Query keeps polling through errors.
- **Pulls**: `pullModel` resolves only on the server's final `{"status":"success"}` line; a stream that ends without one, or fails mid-read, throws `PullConnectionLost`, which `usePull` shows as "Lost the connection to the pull" (not "Pulled") and refreshes the provider's models.
