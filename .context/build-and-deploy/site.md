# Build and deploy: the brochure site

Part of [Build and deploy (`tools/`, `devhelpers/`, `server/Dockerfile`, `server/docker/`, `ui/Dockerfile`, `site/`, `sandbox/`, `deploy/`)](README.md). The static public site in `site/`.

## Containers

- `site/`: static public brochure site (`index.html`, `quickstart.html`, `teams.html`, `security.html`, `coaching.html`, `styles.css`), served by its own small nginx image (`site/Dockerfile`, `site/nginx.conf`, with a `/health`). The apex and `www` hostnames serve this site; `console.<domain>` serves only the static console (`ui/Dockerfile`, `ui/nginx.conf`); `api.<domain>` routes console, agent and machine requests to `agent-server` and redirects its root to the console.
- The brochure leads to the local quickstart and a separate team evaluation path. `quickstart.html` holds the quickstarts, one whole guide per level, picked with the level cards at its top (radios `#lvl-basic`, `-intermediate`, `-advanced`, `-professional`, and `-agent-only` for only the `agent` command; `.qs-guide.guide-<level>` is the guide, and `site.js` checks the radio for a link to `#<level>`): Basic (one container or no containers), Intermediate (the Compose stack, `docs/quickstart.md`'s seven steps), Advanced (the Helm quickstart) and Professional (the production chart, text only). Each guide has its own command box, steps and real screenshots (`quickstart-basic-*`, the numbered `quickstart-NN-*` that `docs/quickstart.md` shows too, `quickstart-helm-*`; web-sized, the sign-in captures cropped to their card), from `quickstart-steps.mjs` run once per level, and each says where the provider is added that a provider is your own, not only Ollama; the homepage keeps a teaser (still `#quickstart`, now the closing panel) and every Try locally link goes to the page. In a guide, tabs (`.qs-tabs`: Basic's one container or no containers, Professional's sizes) and switches (engine, where models run, your terminal: Linux / macOS or Windows PowerShell, which changes line continuations and the installer) pick the command block and the words that go with it. It is radios and `:has()` in `styles.css`: a choice is a radio with an `opt-<choice>` class, and what belongs to another choice of the same switch (`when-<other>`) is hidden while it is checked (`check.mjs` clicks through every level). The homepage's order is the hero, four cards on what it does, how it works (three steps and the diagram), any agent on any machine, session review and AI coaching (section 03: session checks, prompt and workflow advice, cost and caching reviews, linked from the hero at #ai-coaching), three routes to a model, the console, where it runs, teams, then the quickstart panel. `check.mjs` requires its twelve step screenshots to be the ones the guide uses. A new page needs the Pi's front-nginx allowlist too. The homepage shows isolated-demo captures from `docs/screenshots/` as web-sized WebP copies in `site/assets/screens/` (800 and 1440 pixels wide, 400 and 618 for the phone capture, picked by `srcset`; `devhelpers/scripts/screenshots/site-images.py` makes them, leaving the console's sidebar out of desktop captures, so rerun it when `capture.mjs` changes one of its `SHOTS`). Cloudflare and browsers keep the site's stylesheet, script and images for 4 hours, so every page links to them by content hash (`/styles.css?v=<hash>`): `devhelpers/scripts/site/fingerprint.py` stamps the links (`site-images.py` runs it), and `check.mjs` fails while one is stale, so run it after changing `site/styles.css` or `site/site.js`, each linking to its full PNG under `/screenshots/`. The hero is `terminal-grid-dark` (the Live agent view: four demo agents in a 2 × 2 grid, one asking a question, with the quick keys) under a lede on running several agents on different machines and a row of agent names; the console section is a compact two-column gallery with one leading live-session card: a running session (`live-dark`), notifications (`terminal-phone`, in a phone-sized frame), Start an agent, a session, machines and MCP; "Where it runs" lists the ways to add a machine; "Any agent, any machine" (section 02, after how it works) shows three real agents' terminals side by side (`real-opencode`, `real-copilot`, `real-qwen`: OpenCode, Copilot CLI and Qwen Code launched through the current console on an isolated all-in-one container with its own Ollama, captured from `.xterm-screen`; these real-agent captures are separate from the synthetic demo), then three cards, one of them the Android app. `terminal-grid-dark` and `live-dark` are dark demo captures used by the site. `teams.html` covers deployment and operational requirements (with a ladder of what each level runs and an HTML diagram of the scaled Helm install; each quickstart guide also opens with a diagram of its level, `.arch` in `styles.css`, documented in `docs/website.md`); `security.html` covers controls and data boundaries. Compatibility is a native HTML disclosure. The quickstart's commands have two switches, engine (Docker, Podman, Kubernetes with Helm: `docs/quickstart-kubernetes.md`'s install, port-forwards and sign-in) and where models run (CPU, NVIDIA GPU, which adds `deploy/compose/quickstart/compose.gpu.yaml`; for Helm a note on giving the machine's `ollama` container a GPU): radio buttons and CSS `:has()` show one of five command blocks and the notes for the choice, so they work without JavaScript; `site.js` copies the block shown (`data-copy-shown`). `docs/website.md` records implementation/test evidence and the minimum version for governance/cluster features; Helm image defaults must be checked separately. The existing console link is secondary and requires an account for that deployment. The architecture is semantic HTML/CSS and stacks vertically on small screens. `site.js` progressively enhances the mobile menu, the copy button and the screenshot links (a `<dialog>` viewer over the page; a modifier-click still opens the PNG); content and navigation remain usable without it. No application API calls or third-party assets are used.
- Every quickstart guide is in two parts: setting it up (the numbered steps, listed at the top under "Set it up, step by step") and a separate **Stop or remove it** section at the guide's end (`#<level>-remove`, linked from the step list), which says how to stop without removing and holds the removal commands with a Keep data / Purge data segmented control, styled like the install switches. The removal commands follow the switches chosen in step 1, since the switches are scoped to the guide. Data is kept by default. Basic uses container removal or the local uninstaller; Compose adds down -v for purge; Helm uses namespace deletion. Agent-only commands use --only agent. Namespace deletion does not erase external databases, object storage, backups or retained storage; the production box explains this limit. CSS switches the commands without JavaScript, and the copy buttons copy the selected variant.
- `site/assets/` contains editable SVG branding and browser-rendered PNG social/app icons. `robots.txt`, `sitemap.xml`, `site.webmanifest` and homepage metadata use the apex hostname. The Dockerfile explicitly copies the public assets and selected screenshots. `devhelpers/scripts/site/preview.mjs` serves the same allowlist on loopback; `check.mjs` checks all five pages at 375/768/1440 px, cross-page navigation, quickstart inputs, interactions and assets, and optionally renders branding exports with `--render-assets`. Browser captures go to gitignored `.test-site/`. See `docs/website.md` for commands and claim evidence.
- Bump the brochure stylesheet URL's `v` query in all five public HTML pages when changing `site/styles.css`: public CDNs may keep the previous CSS after a deployment.
