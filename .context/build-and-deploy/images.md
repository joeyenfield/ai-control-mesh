# Build and deploy: images

Part of [Build and deploy (`tools/`, `devhelpers/`, `server/Dockerfile`, `server/docker/`, `ui/Dockerfile`, `site/`, `sandbox/`, `deploy/`)](README.md). The container images: the server, the sandbox and the all-in-one image.

## Containers

- The root `.dockerignore` excludes local virtual environments, agent metadata/history, `output/` and generated `.screenshot*`, `.test-*` and `.tmp-*` directories. Keep these out of the context: Compose's Windows context validation can fail on their private ACLs before the container engine sees the build.
- `server/Dockerfile` (built from the repo root, because it needs `ui/`): builds the console with Node, then a python:3.13-slim image running as uid 10001, with `docs/`, `VERSION` and `benchmarks/tests`, `AI_PROXY_HOME=/app` and `AI_PROXY_UI_BUILD=0`. It copies no default config (a new database is seeded from `defaults.py`) and has no entrypoint script: `ENTRYPOINT ["agent-server"]`. Volumes `/app/logs` (the server's log, and the SQLite database when no `AI_PROXY_DATABASE_URL` is set) and `/app/certs` (`first-user-password`); `/app/config` and `/app/auth-state` exist, owned by the image's user, only so an older install's volumes can be mounted for the import. Port 9999. Pass `--build-arg AI_PROXY_VERSION` to match a `dist/` folder (no git in the image).
- `sandbox/`: an image with `agent`, `agent-machine`, the npm coding agents (`AGENTS`) and the Antigravity CLI (`ANTIGRAVITY=1`: Google's `install.sh --dir /usr/local/bin`, which checks the binary's SHA-512 against its manifest; it takes the newest release, so it isn't pinned like Ollama). Its entrypoint signs both in through device approval (or a setup code), retrying a failed sign-in after a wait that doubles to 15 minutes rather than exiting (a restart policy would otherwise loop it, asking for codes), sets launches on for `/workspace` only (containers always off; servers on unless `AGENT_SERVERS=off`), and runs `agent-machine run`. agent-machine only probes its own loopback, so `AGENT_OLLAMA`/`AGENT_LLAMACPP` (`host[:port]`) make the entrypoint run `socat` relays from `127.0.0.1:11434` and `127.0.0.1:9931` to model server containers next to it; tunnels then reach them like local ones. The image copies Ollama (`OLLAMA_VERSION`, pinned) from the `ollama/ollama` image with only its CPU backends (the top-level files of `lib/ollama`; every GPU backend is a subfolder, dropped), into `/usr/local/bin` and `/usr/local/lib/ollama`, where `ollama` looks beside itself; servers on starts it from PATH. A relayed `AGENT_OLLAMA` holds 11434, so the entrypoint warns that the console manages that one instead. For OpenShift's restricted policy (a random user in group 0), `/home/agent` and `/workspace` are `chgrp 0`/`g=u` and `/etc/passwd` is group-writable; the entrypoint adds a passwd line for a nameless user, falls back to `HOME=/tmp/agent-home` when the home isn't writable, and maps `AGENT_DATA_DIR` to agent-machine's `AI_PROXY_MACHINE_DATA`. The image carries `libgomp1` because llama.cpp's GitHub Linux builds (what the console installs with servers on) need it and node's slim base lacks it.
- Sandbox first start prints one device code for both programs; persistent shared home credentials refresh later. Password/key bootstrap is removed.
- `sandbox/Dockerfile`'s runtime stage is `ubuntu:24.04` with Node from the `node:22-bookworm-slim` image (`COPY --from=node /usr/local/`), the `PACKAGES` build argument (everyday tools: git, gh, ssh/sftp, ping, dnsutils, build-essential, Python with pip/pipx and `python-is-python3`, so `python` works, ...), `EXTRA_PACKAGES`, and passwordless sudo for `agent` unless `AGENT_SUDO=0` (agents may install tools; `AGENT_APT_PACKAGES` installs on start). Ubuntu's user 1000 is `ubuntu`, renamed `agent` (node's was `node`). The all-in-one image repeats these arguments.
- `deploy/compose/allinone/` is the `ai-control-mesh` image: the whole system in one container, to try it (`docs/local.md`). Its Dockerfile repeats `sandbox/Dockerfile`'s stages (Go programs, Ollama's CPU build, the agents on node and `agy`; `server/tests/test_allinone.py` keeps `OLLAMA_VERSION`, `AGENTS`, `ANTIGRAVITY` and the base images in step), builds the console, and lays the server out in `/opt/mesh` as the release bundle does (`pip install -e`, `BUILD`), so `/opt/mesh` is its `ROOT`. `entrypoint.py` runs `local.start(overrides=...)` with `AI_PROXY_HOST`/`AI_PROXY_AUTH_HOST` `0.0.0.0` and `AI_PROXY_LOCAL_HOME=/data/server`, signs agent-machine and agent-proxy in once through `deploy/compose/quickstart/machine.py`'s `sign_in` (copied in as `quickstart_machine.py`: the issuer's device flow at the fixed `localhost:19999`/`20000`, so the host must publish those same ports), switches launches, files, commands and servers on for `/workspace`, then supervises `agent-machine run` and the two processes, stopping all when one stops. `MESH_ADMIN_PASSWORD` makes `admin` an environment user. Volumes `/data`, `/home/agent`, `/workspace`. A GPU: the build argument `OLLAMA_GPU` (empty by default, so `ai-control-mesh` stays CPU only) names the Ollama GPU backend folders to keep. `release/local.py` builds the same Dockerfile with `OLLAMA_GPU=cuda_v13` as `ai-control-mesh-gpu` when `services --image gpu` is selected, which `deploy/compose/allinone/compose.gpu.yaml` runs with the NVIDIA GPUs as the CDI device `nvidia.com/gpu=all`; `devhelpers/allinone/compose.gpu.yaml` builds it from the checkout as `localhost/ai-control-mesh-dev-gpu`. `docs/gpu.md` is the guide for setting up Podman or Docker; `test_allinone.py` checks the files and the release catalog.
