# Build and deploy: scripts

Part of [Build and deploy (`tools/`, `devhelpers/`, `server/Dockerfile`, `server/docker/`, `ui/Dockerfile`, `site/`, `sandbox/`, `deploy/`)](README.md). The developer and release scripts, in `.sh`/`.ps1` pairs.

## Scripts (`.sh`/`.ps1` pairs; change both)

The quickstart and all-in-one helpers provision one shared auth file (`credentials_path` in quickstart/machine.py); provisioning reads that same file after token refresh. The sandbox signs in once through agent-machine. Full installers may invoke both login commands for setup, but the second reuses the shared login and still applies machine permissions. Termux restart recognizes the shared file as well as the old machine-only file. Machine home/data overrides never choose a separate auth profile.

The Termux branch is Unix-only; its PowerShell twin has no PRoot flow. Probe `proot-distro install --help`, never `kill`: PRoot-Distro 5.3.0 has no `kill` command. The generated `.mesh-termux-stop.sh` uses the machine, proxy and local server stop commands inside Ubuntu. The foreground session polls local status and exits after shutdown; unrelated guest shells stay open.

The server's agent-only one-line installer and the archive `tools/dist/install/install.sh` also detect native Termux using both its prefix/version and the resolved `sh`. They default to `$PREFIX/bin` and turn `--service` into a nonfatal skip, so the one-liner reaches sign-in and background start instead of failing on systemd. Inherited Termux variables in a PRoot guest do not select this path. `server/tests/test_installer.py` exercises both real scripts with fake programs and an isolated Termux prefix; no real service or fleet is touched.

The one-line installer pair tracks failed sign-in and machine startup separately from copying binaries. Its final message reports incomplete setup instead of saying Done after either fails. Android programs also normalize Termux's duplicated executable argument before dispatch (`settings.CommandArgs`, Python's `common.command_args`), so sign-in reaches the login command.
The native Termux `uninstall-local.sh` uses the installer's `.mesh-termux-prefix` marker to identify its private bound home, stops the guest, then uses `proot-distro remove ai-control-mesh` to remove the dedicated Ubuntu environment. It removes only the matching `mesh-termux` link. Without `--purge`, the bound home remains for a later install; with `--purge`, it deletes that whole home (including the issuer state and signing key). A failed guest removal leaves the bound home in place so the user can close remaining shells and retry. The ordinary Unix uninstaller still works inside the guest but only removes the server's own folder there.

The release bundle also carries `deploy/compose/quickstart/machine.py`, `devhelpers/release_scripts/release/local_quickstart.py` and `devhelpers/release_scripts/release/termux_quickstart.py`. On a desktop, the installers run `local_quickstart.py signin` (admin's device approval with the first-user password, merged into the shared credentials file under its lock), then `local_quickstart.py machine` (a new machine gets launches, commands, files and servers in `~/projects`; an existing one keeps its settings). There are no prompts. `--no-machine` skips the second step and `--no-login` skips both. `AI_PROXY_LOCAL_INSTALLER=1` drops the manual commands from `agent-server local start`'s next steps. The Termux guest runs the normal installer with `--no-login`, then the quickstart helper uses the local admin password with the issuer's normal device approval flow to save shared credentials. It configures the new machine's supported functions, keeps containers off in PRoot, adds `/root/projects`, and starts it. Reinstalls preserve existing machine settings other than containers. No device code or permission menu is presented in this path; the console still requires browser sign-in.

The release's `install-local.sh` detects native Termux by its prefix and shell path, before platform selection or Python dependency installation. A separate flow provisions the dedicated `ai-control-mesh` Ubuntu 24.04 guest through current PRoot-Distro, binds a private Termux data folder as its home, and invokes the same version's installer there with Python clients and no tray. Inherited Termux variables alone never trigger this inside a guest. `mesh-termux` manages foreground start, status, shell and stopping the guest's process tree. Generated guest scripts preserve installer options and reuse the private home on update. `server/tests/test_release.py` covers dispatch, guest failure, options, script parsing and lifecycle commands. Real Android execution remains experimental pending device validation; `docs/local.md` records the limits and storage paths.

- `build-client`, `build-machine` (into `client/bin`, `machine/bin`), `build-dist` (wraps `tools/dist`; `PACKAGES=1` / `-Packages`), `agent` (build and run), `dev` (API with reload + Vite).
- `install-local` (`docs/local.md`): finds Python 3.11 or later (else stops with a message), makes `.venv` in the checkout when the system's Python is externally managed (PEP 668), `pip install -e server`, the console with npm when it's there, `agent` and `agent-machine` with the build scripts when Go is there (else `pip install python/`), then `agent-server local start` (`server/agent_server/local.py`). Never run it on the dev machine as is: it rebuilds `client/bin` under the running agent-proxy.
- No pair: `start-ollama.sh`, and `devhelpers/scripts/https/setup-https.ps1` (Windows: nginx + win-acme for Let's Encrypt, filling in `nginx.conf.template` and `nginx-https.conf.template`: the brochure site on the apex/`www` (`-SiteBackend`, :8080), the console on its hostname (`-ConsoleBackend`, :8081), the issuer on `auth.<domain>` (`-AuthBackend`, :10000) and API traffic on `api.<domain>` (`-Backend`, :9999)).
- `devhelpers/release_scripts/deploy.sh`/`.ps1`, `deploy-remote.sh` and `deploy-setup-remote.sh` (the one-time `--setup`: the ssh key and passwordless sudo for docker there) are gitignored, maintainer-only helpers. From clean master they push the checkout, call the local `services --publish` release with `--receipt dist/deploy-services.json`, built for `linux/arm64` (the server is a Raspberry Pi; they run `podman-arm64` first), then stamp `build-dist` with that receipt's version. They update the remote checkout and copy the matching downloads. The remote helper checks checksums, pulls the already-published service image once, and starts only agent-server, agent-auth and the deployment-specific console. It does not wait for Actions or redeploy the website. An explicit Version option selects a stable release; otherwise it uses a snapshot. Both remote health endpoints must answer and the server must report the built version. Settings remain `AI_PROXY_DEPLOY_TARGET`, `_DIR`, `_HEALTH`, `_PASSWORD`, `_ENV_FILE` (default `/etc/agent-mesh/compose.env`). These helpers stay untracked.
- `devhelpers/release_scripts/podman-arm64.sh`/`.ps1` prepare Podman for ARM64 image builds on x64: they start the Podman machine if it is stopped and register `qemu-aarch64`. Under WSL the machine's `systemd-binfmt` can't do it (`/proc/sys/fs/binfmt_misc` is an unreadable autofs mount there, and restarting that service hangs), so they mount `binfmt_misc` at `/run/binfmt` and write the machine's own `/usr/lib/binfmt.d/qemu-aarch64-static.conf` to its `register` file. The registration lasts until the machine restarts; the scripts do nothing when it is already there.
- `devhelpers/scripts/screenshots/`: `demo.py` (a self-contained demo server on :8199 with fake machines and backends; its temporary home has its own SQLite database, seeded with `config_io.apply` and the shipped model tuning; `--capture` runs the screenshots and stops it, `--stop` stops one left running), `traffic.py` (drives agent traffic through it) and `capture.mjs` (Playwright screenshots into `docs/screenshots/`). `pipelines/screenshots/run.py` runs `demo.py --capture` in a disposable `mcr.microsoft.com/playwright` container (its tag and `playwright-core` pinned together) and copies the PNGs back; `pipelines/Jenkinsfile.screenshots` is its manual multibranch job, which can push the result to the branch.
