# Build and deploy: releases

Part of [Build and deploy (`tools/`, `devhelpers/`, `server/Dockerfile`, `server/docker/`, `ui/Dockerfile`, `site/`, `sandbox/`, `deploy/`)](README.md). Local release builds: images, installers and the tray.

## Containers

- `devhelpers/release_scripts/release.ps1|.sh` invokes the shared standard-library Python orchestrator `release/local.py`. Its `IMAGES` catalog selects `website` (only `ai-control-mesh-site`) or `services` (default `agent-server`, including auth and console; explicit `sandbox`, `allinone`, `gpu`). Builds run directly on local Podman, with native Linux x64 by default, cached layers, Docker image format and no injected HTTP proxy. Repeated `--platform` builds a manifest; non-native targets require local emulation. `--archive` exports single-platform Docker archives. Each snapshot gets a unique UTC/commit tag and a PEP 440 local version; receipts/checksums live under `dist/releases/<type>/<tag>/`. `--plan` writes nothing. `--publish` directly pushes selected images to a registry or uploads installer files through `gh`, requiring committed tracked changes. All image builds finish before pushes begin. `--stable` requires a clean checkout at the existing matching version tag; only `--stable --publish --promote` updates latest. There are no Actions workflows, and pushes/tags have no build side effects. Website and service tags are independent (`AI_PROXY_SITE_IMAGE_TAG` and `AI_PROXY_IMAGE_TAG` in the server Compose stack). `docs/releases.md` covers every command, prerequisites and retiring queued Actions runs.

- **The tray** (`agent-tray`, `python/agent_py/tray.py`) comes in with the wheel's `tray` extra. The release's web installers install the wheel into the server's venv (always, for the tray; only `--python` links `agent`/`agent-machine` from it) and the server's one-liners into the `agent-py` venv, when there's a desktop (Windows, macOS, `DISPLAY`/`WAYLAND_DISPLAY`; there's no root check), unless `--no-tray`/`-NoTray`. Failing to install it never fails the install. They link or copy only `agent-tray`, run `--autostart on`, and start it detached at the end. pip fetches the server's Python dependencies (and pystray and Pillow for the tray) from PyPI: the release's hashes cover only its own files. `tools/dist`'s wheel writer carries `[project.gui-scripts]` into `entry_points.txt`'s `[gui_scripts]`. The installer tests use a fake wheel whose `tray` extra is empty and whose `agent-tray` only prints, with `PYTHONPATH` cleared so the real `agent_py.tray` can't set the dev computer's own autostart.
- `release/local.py installers` builds `ui/dist` and `tools/dist -android=false` locally, with intermediate archives under `dist/local-builds/<version>/` and final files under `dist/releases/installers/<tag>/files/`. Targets can be limited with repeated `--target`. Only `--publish` creates a GitHub Release (snapshots are prereleases at the source commit, stable builds verify the existing tag). No published assets are overwritten. Then `devhelpers/release_scripts/release/release.py` writes the release's flat files: the server bundle `ai-control-mesh-X.Y.Z.zip` (`VERSION`, `BUILD`, `LICENSE`, `server/` sources, `ui/dist` without the UI sources so `ui_build` never rebuilds, `docs/`, `benchmarks/tests`), every archive, the wheel, `SHA256SUMS`, and the web installers `install-local.sh`/`.ps1` filled in from the templates beside it (`{{BASE}}`, `{{VERSION}}`, `{{BUNDLE}}`, `{{FILES}}`, each checked to be plain URL, version and file-name characters). The installers trust only the hashes written into them. They unpack the bundle into `<instance home>/app/<version>` (the `local.py` folder; keep the two in step), `pip install -e` its `server/` into `<home>/venv` so the bundle is the server's `ROOT`, stop a running instance first, remove older `app/` folders, link `agent-server` into the prefix, run `agent-server local start`, then unpack each archive and run its own installer (`AI_PROXY_ONE_LINER=1 --prefix`) and run `agent-machine config` through the terminal before machine sign-in. The menu chooses permissions instead of enabling launches/files automatically; `login --enable=` keeps an inherited enable list from overriding those choices. With no terminal or `--no-login`, permissions stay unchanged and setup prints the commands for later. On Windows the archive's `install.ps1` runs in a child PowerShell with `-ExecutionPolicy Bypass -File` (the server's `/install.ps1` does the same): it's a file on disk, which the default policy refuses, unlike the `irm | iex` text; the tests pass `-ExecutionPolicy Bypass` themselves, so they can't show a regression there. `--help` prints a `usage` heredoc, since a script piped into `sh` has no file to read its header from. The last lines repeat the console's address and the password file. `uninstall-local.sh`/`.ps1` (the same folder, copied into the release as they are) undo it: the tray's autostart, agent and agent-machine through the bundle's own `server/agent_server/install/uninstall.*` (before the server stops, so `--purge` can sign them out), the `agent-server` link, `app/` and `venv/`, and the data only with `--purge`; keep their folders in step with the installers'. `version.py` takes the version from `BUILD` when there's no git. In PowerShell 5.1 every native call goes through `Invoke-Program`: with `ErrorActionPreference = Stop`, redirected stderr (Authlib's deprecation warning, say) would otherwise abort the install. Test them with `--base-url http://127.0.0.1:<port>`, a local `http.server`, `AI_PROXY_LOCAL_HOME` and `--prefix` in scratch folders, spare ports, and on Linux a throwaway user in `FedoraLinux-44` (`server/tests/test_release.py` covers the files).
