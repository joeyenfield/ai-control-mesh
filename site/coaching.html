From evidence to advice

Review what happened.
Choose what to improve.

Every session an agent runs through the server can be reviewed. Open it from Sessions and choose Review. The tab has three parts: checks, the numbers behind them, and an AI review.

  1. 1

    Read the checks

    The server runs a fixed set of checks as the tab opens and gives the session a score. No model is involved, so they are instant, free and the same every time. Check again updates a session that is still going.

  2. 2

    Ask a model for advice

    Pick a review topic, choose a provider and model, and optionally add your own question. The answer streams in: a summary, numbered suggestions with the most valuable first, and what went well.

  3. 3

    Try the useful suggestions

    Use a revised prompt, a shorter instruction file or a change to your tools. Review a similar task afterwards and compare the score, tokens and cost.

Built-in checks

24 checks in five areas.
No model needed.

Each finding has a level (high, medium, low or a note), what was seen and what to try. Where the server can work it out, it also says about how many tokens the problem cost over the session. Findings are listed worst first.

Context

What every call carries before any work is done.

  • Large system prompt: instructions of about 8,000 tokens or more on every call.
  • Many tool definitions: tool descriptions of about 10,000 tokens or more.
  • Most tools never used: 30 or more tools defined and under a quarter called, with the idle MCP servers named.
  • Very large or fast-growing context: a call that read 70% of the model’s context, or a context that gained 5,000 tokens a call.
  • Many images in the conversation.

Tools

How efficiently the agent searched, read and ran commands.

  • A lot of searching for files: searches and listings that make up over 35% of tool calls.
  • The same files read again and again.
  • Very large tool results: about 10,000 tokens or more from one call.
  • Many failed tool calls: a wrong path or command, a missing tool, edits that don’t apply.
  • The same call repeated with the same input: often a looping agent.

How it went

How the task was set and steered.

  • A short first prompt for a long task: under 80 characters for 30 or more model calls.
  • A lot of steering: 20 or more messages typed.
  • A very long session: 150 or more model calls.
  • The conversation was compacted into a summary.
  • Many sub-agents.

Reliability

Calls that failed, stalled or stopped early.

  • Model calls failed: 3 or more, over 5% of calls.
  • Calls were rate limited with 429.
  • Replies were cut off before the model finished.
  • Slow to start answering: half the calls waited over 15 seconds for the first token.

Cost

Model choice and caching.

  • Most calls went to a frontier model: 60% or more of the calls.
  • Little of the prompt came from the cache: under half, on a provider that reports caching.
  • The cache ran out while the session sat idle: calls more than 5 minutes apart that wrote most of the prompt to the cache again.

What the checks need

Checks on tokens, failures, caching and timings always run, because the server records those for every request. Checks on the system prompt, the conversation and the tools read the session’s payloads, so they need payload capture: start the agent with --trace, or turn capture on for the session. Without payloads, a note says so and the session is checked on its numbers only.

Payload token counts are estimates at four characters a token. Call token counts are what the provider reported.

The score

One number to compare sessions.
The findings say what to do.

From 100, less each finding

A session starts at 100 and loses 18 points for each high finding, 9 for each medium and 3 for each low. It reads Efficient from 85, Some waste from 65, Wasteful from 40 and Very wasteful below that. Each finding shows the points it took off.

A score for each area

Context, Tools, How it went, Reliability and Cost each get their own score, worked out the same way. A session can be tidy on tools and wasteful on context. Choose an area to see only its checks.

One cause counts once

Some checks see the same cause from different sides: context size, tool loops and caching. In each group the worst finding costs its full points and the others a third of theirs, so one problem doesn’t sink the score several times.

The provider’s doing doesn’t count

Slow first tokens and failures that were mostly the provider’s own (5xx errors) are shown and passed to the AI review, but take no points. Rate limits still count: they are often caused by too many agents at once or the organization’s limit.

Model tiers

Each call is placed in a tier from its model’s input price in the server’s price table: frontier from $4 per million input tokens, small under $1.50, mid-range between. Local models and models with no price are never counted as frontier. On a subscription, frontier calls use up the plan’s limits rather than money.

Where the points went

The top of the tab sums it up: the score, how many findings there are at each level, about how many tokens they add up to, and the main cause. The AI review receives the same summary, so it starts with what cost the most.

What was measured

The numbers behind every finding.
Check them yourself.

Three charts

  • The context, call by call, for the main chat, so sub-agents don’t blur it.
  • What the context holds: the system prompt, tool definitions, tool results, tool calls, replies, thinking, typed messages and notes the agent adds.
  • Model calls by tier: frontier, mid-range, small, local and no price.

Tables that open

  • Models: calls, tokens read and written, and estimated cost for each.
  • System prompt sections: the largest twelve with their sizes. Look here before trimming an instruction file.
  • Tool definitions and MCP servers: the largest, and the ones never called.
  • Tool calls and shell commands: how often, failures and result sizes.
  • Failed tool calls, grouped by tool and error.
  • Files changed, and files read three times or more.
  • The main chat, step by step: each message typed, the tool calls that followed and the tokens they added.
  • Sub-agents: what each was asked, its model and its calls.

Focused coaching

Nine review topics.
Ask the question that matters.

Each topic asks its own question, sends only the parts of the session it needs, and includes the findings of the checks in its area. What gets sent shows the exact data, checks and prompt before you start.

The whole session

The few changes, up to six, that would save the most across everything.

Context and prompt

What could be removed, shortened or loaded only when needed, largest part first, and what each change would save per call.

Instruction files

An editor’s audit of the system prompt section by section: what belongs in every call, what should move out, and an outline of a shorter version.

Tool use

What to tell the agent or set up in the project so it makes fewer and smaller calls, quoting the command or search and its replacement.

Prompts and workflow

Whether the task was stated well, how much steering it took, where planning first or a new session would have helped, and a better version of a weak prompt.

Where the context grew

The moments the context jumped, what caused each and what it cost afterwards, and where to clear, compact or hand work to a sub-agent.

Cost and caching

Which habits or settings would lower the cost and by roughly how much, and whether a smaller model could have done part of the work. Savings depend on the task and provider.

Failures and speed

Failed tool calls grouped by cause, what most likely caused each failure or wait, and what to check.

Lessons for the project

The lines to add to your project’s instruction file, written out, from what the agent had to discover for itself, so future sessions start with that knowledge.

Every topic gives the model the same rules: work only from the data, say when it can’t tell, don’t repeat numbers back, be specific and don’t invent facts about the project.

During a review

Watch it work.
Come back to it later.

Clear progress

A running review shows where it is and how long it has taken: Sent while the model reads the data, Thinking while a reasoning model works (its thinking shows as it arrives, with a token count, so a quiet minute isn’t mistaken for a hang), Writing as the answer arrives, then Finished. Stop ends it early.

Keeps running while you browse

Leave the tab or go anywhere else in the console, and the review carries on. Open as a session shows it in the chat view. Closing or reloading the console stops it, because the page reads the reply.

Recorded like any agent call

A review is a private session of its own with its payloads captured. It shows on Sessions, Traffic and Requests, counts toward your usage limits, and has a cost on a paid provider.

Earlier reviews

Finished reviews are listed under Earlier reviews to read again. A review lasts as long as its own session. Someone else’s review of a session you share shows only if they share the review’s session too.

Your own prompts

Review for what your team cares about.

Site admins can replace the set of review topics on Server settings › Review prompts, as one YAML document. Each prompt chooses its question, the session data it sends and the checks whose findings go with it. Use the shipped prompts goes back to the nine above.

SERVER SETTINGS / REVIEW PROMPTS
prompts:
  - id: risky-commands
    title: Risky commands
    about: What the agent ran that deserves a second look.
    focus: >-
      Look at the shell commands the agent ran. Say which could have changed
      something outside the project folder, and what rule in the instruction
      file would prevent each.
    data: [session, commands, errors, edits]
    metrics: [tool-errors, repeated-calls]
    suggestions: 3

Nineteen kinds of data to choose from

Pick what a prompt sends, such as the session summary, tokens, cost, the context timeline, the system prompt outline, tool calls, shell commands, searches, edited files and errors. The server adds the shared rules and the shape of the answer around your question.

From a script

GET /api/sessions/<id>/review returns the measurements, findings, score and prompts as JSON, so a script can check sessions after a run. The prompts are part of the server’s settings, so agent-server config export and import carry them.

Your choice of reviewer

Choose the model.
Understand what it receives.

Local models or hosted APIs

Choose any provider you can use that supports OpenAI Chat with the server’s own credentials: a model server on one of your machines, or a hosted API or gateway with a key stored on the server. Providers that need the agent’s own credentials are not offered. Larger models give better advice; small local ones tend to repeat the numbers back.

Selected evidence, at most 16,000 characters

The model receives only what the chosen topic lists: measurements and findings, the start of the system prompt and its section titles, the names of tools, MCP servers and files, short command lines and search patterns, the start of each kind of tool error, and the first few messages typed. It never receives the full transcript, file contents or whole tool results. Pick a provider you would send that to.

The review suggests changes to your workflow; it does not change your code or settings. Check its advice against what you know about your project. Cost figures are estimates, and a session review is not a correctness or security audit of the code. Anyone who can see a session can review it.
